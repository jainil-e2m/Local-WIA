# sql/

- `migrations/` — Alembic, the **only** schema owner. `env.py` imports `backend.models.db.Base`; revisions live in `migrations/versions/`.
- The application never calls `Base.metadata.create_all()`.

Run from the repository root:

```bash
alembic -c backend/alembic.ini upgrade head
alembic -c backend/alembic.ini revision --autogenerate -m "describe change"
```

Review every autogenerated revision before committing it. Partial indexes, check constraints and data migrations need hand edits.

## First production deploy: one schema file

Production starts empty, so it is created from **`schema.sql`**: the final schema, plus the Alembic revision marker. It isn't built by replaying each migration.

```
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f backend/sql/schema.sql
```

- Run it **once, on an empty database only**.
- **After that, every change is a normal migration** (`alembic upgrade head`), because production then holds data.
- Regenerate the file whenever a migration is added: `python -m backend.scripts.schema_export`. This needs the compose `db` running.
- Checked 4 Nov: applying `schema.sql` to an empty database gives the same schema as the models (0 differences, revision c06a20261102).
- 6 Nov: regenerated at revision c09a20261106. On Railway the web service's pre-deploy step runs `alembic -c backend/alembic.ini upgrade head`, which builds the same schema on the empty database (the image has no `psql`), and applies later migrations the same way.
