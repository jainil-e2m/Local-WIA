# Before production

What the 30-day / three-client ingestion test deliberately simplified or left out, and what must change before production. Each item names the setting or file that changes. The pipeline, schema and adapters are the production ones: removing the test window is `INGEST_WINDOW_DAYS` unset (or `kb backfill --full`).

## 1. Test-only simplifications (must change)

| # | Area | Test behaviour | Production requirement | Where |
|---|---|---|---|---|
| P-01 | **Gmail qualification.** *Done 4 Nov: the reader records header metadata for every message, and since BF-2 (`gmail-v3`) no message body is stored at all; it is read from Gmail on demand* | Only messages with an approved client contact in From/To/Cc are fetched. Nothing at all is recorded for any other message | Header metadata (from, to, cc, thread, labels, time, hash, no body) for **every** message, body only for qualified ones. Needed for "waiting on us", last contact, coverage accounting and **re-qualification** when a new contact is approved (Ingestion design §4.2, D-2) | `adapters/gmail.py` `backfill_page` |
| P-02 | **Re-qualification** | **Built 6 Nov.** Gmail, Calendar and Fathom keep a pointer for every item; approving a contact or reactivating a client queues `qualify.recheck`, which attaches Gmail pointers at once and refreshes Calendar events and Fathom meetings one by one (at most 500 per approval) | `qualify.recheck` job: when a contact is approved, re-run qualification over stored metadata (Gmail) and re-scan Calendar/Fathom for that contact | new job in `workers/jobs/intake.py` |
| P-03 | **Dubsado / finance mail** | Dubsado notifications don't include client addresses, so client-only qualification never fetches them | An explicit sender rule (`noreply@dubsado.com` → qualify, domain `finance`) plus project-label → client mapping in review | `adapters/gmail.py` |
| P-04 | **Incremental sync** | **Built.** The workers run `sync.sweep()` when `SYNC_SCHEDULER_ENABLED` is on; streams switch on after their first full copy; `kb backfill` uses the resumable sync path. Production starts with the scheduler off (backfills on command). Still open: the Fathom webhook route | Per-provider incremental cursors (Gmail `historyId`, Calendar `syncToken`, Drive `changes`, Slack `ts` + 7-day re-scan, ClickUp `date_updated_gt`, Fathom re-poll), a scheduler loop in the runner, an operator path to enable streams, the Fathom webhook route (`FATHOM_WEBHOOK_SECRETS`), and switch-over from backfill to incremental | `workers/runner.py`, `services/intake/sync.py` |
| P-05 | **Calendar occurrences** | `singleEvents=true` over the window; full-history mode expands up to one year ahead | Sync masters/exceptions with `syncToken`, materialise occurrences for a rolling horizon, handle HTTP 410 with a tracked resync (design §4.2) | `adapters/calendar.py` |
| P-06 | **Deletion detection** | Not exercised. Records only ever become `available`. | P-08 | **Extraction hand-off** | `record.extract` work items are queued in lane `analysis`; no worker consumes them | The extraction slice consumes them (or they're pruned) | `workers/runner.py` lanes |

## 3. Production hardening not in this slice

- **Webhooks:** none. Polling first by design (AR-15).
- **Ops API:** behind an `OPS_TOKEN` header. Replace with the Command Center hand-off and KB sessions (AR-04).
- **Credentials:** come from `backend/.env` locally. In Railway, use deployment variables and move the Google refresh token out of `frontend/.data`.
- **Slack:** attachments are referenced, not downloaded. Gmail attachments are referenced, not parsed. Drive shortcuts are recorded, not followed.
- **Sheets:** tabs over 5,000 rows are stored partially and marked `partial`.
- **Observability:** no error tracker or external uptime check yet (AR-24). Logs are JSON to stdout, IDs and counts only.
- **Backups:** PITR check, daily external dump and a restore drill (AR-25).
- **Throughput:** one worker process. Add `bulk` concurrency per provider limits after measuring the full inventory (AR-12).
- **Repository:** probe JSON with client personal data is still in git history (AR-13). The root `.gitignore` now prevents new `.env` / `.local` commits.

## 4. Full-history backfill on Railway (before client delivery)

**Plan.** Once the major backend components are built, deploy the backend to Railway and run one full-history backfill (`kb backfill --full`) of every approved source for every active client. The data goes into the production database. Every later component (extraction, actions, profile, briefs, health) reads from this stored data rather than calling providers, and the frontend is mapped onto it last. The backfill finishes **before client delivery**.

Because every later component builds on this one load, the load has to be correct the first time. Re-running it means re-fetching the whole history from every provider. These items must be done before the full run starts:

| # | Item | Why it matters for a one-time full load | Where |
|---|---|---|---|
| B-01 | **Done in code 4 Nov (BF-1; `tests/services/test_http.py`).** Google rate limits arrive as HTTP 403, not only 429. Every 403 was treated as scope denied | A long run will hit Gmail/Drive/Calendar quota. Per item: false "inaccessible" gaps and a `partial` run. Per page: the job is blocked and the whole run fails. Read the error `reason` (`rateLimitExceeded`, `userRateLimitExceeded`, `quotaExceeded` → throttled, back off and retry; `insufficientPermissions`, `forbidden` → scope denied) | `services/shared/http.py` |
| B-02 | **Implemented: atomic page publication and fenced failure recovery** | Page effects, checkpoints, continuation jobs and work-item success share one transaction in both publishers. Database integration tests exercise worker death before/after commit, rollback, lease expiry, duplicate delivery and lost commit confirmation. Pre-fix runs still need reconciliation; follow the [cutover procedure](docs/atomic-publication.md) before production | `pipeline.py`, `workers/runner.py`, `workers/queue.py` |
| B-03 | **A run can't resume** | One page failing permanently fails the run, and the next run starts from the beginning (`sync_cursors` is written, never read). Resume from the last stored cursor, and allow only one running run per scope. **Partly built:** on the sync path `sync.resume()` restarts a failed/partial run from its checkpoint and one stream runs one run at a time; it has no CLI yet and `kb backfill` doesn't use it | `pipeline.py`, `services/intake/sync.py` |
| B-04 | **Reclassifying a record's domain only tags the new version** | Development only, no code change: the 27 contract/pricing units left as `profile` in older versions by the 30-day test were re-tagged `finance` in the local DB (28 Oct). If a classification rule changes again before production, fix the local data the same way. The production full run starts on an empty database, so domain rules must be final before it; then no stale tags exist | local DB; `adapters/drive.py` rules |
| B-05 | **Updates to already-stored records go through client qualification again** | A cancelled event or edited invite without an approved contact is dropped and the old version stays current. Records already stored always accept their updates. **Built on the sync path** (`admission.py` lookup used by `adapters/readers.py`); the one-shot backfill adapters still re-qualify | `adapters/calendar.py`, `fathom.py`, `gmail.py` |
| B-06 | **One Gmail search holds every client's contacts** | At 30–40 clients the query may exceed the URL limit and fail as a bug. Split the contacts into batches | `adapters/gmail.py` |
| B-07 | **Parser changes don't bump `parser_version`** | Changing a parser mid-run would mix two parser outputs under one label | each adapter |
| B-08 | **Throughput and size** | Size Railway Postgres storage and the `bulk` worker count from the Phase 0 inventory (AR-12); confirm PITR or a dump runs before and after the load (AR-25) | Railway config |
| B-09 | **Retention decision (Q-4)** | Full normalised text is kept for every unit. WIA confirms that is acceptable (or sets the duration, P-07) before the whole history is copied | WIA decision |

After the run: `kb report`, then the source-by-source gap report for WIA sign-off (FR-INT-02).
